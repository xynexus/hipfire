# #377 resolved: the assertion was on the wrong statistic

Status: **RESOLVED 2026-09-02.** GitHub issue #377 —
"tiny-prefill: qwen3_5_moe_indexed batched prefill diverges from per-token
reference (q8 AND kvarn) on gfx1103".

## What the issue reported

`tests/tiny-prefill-gate.sh` failing both `qwen3_5_moe_indexed` cells, at
7.16e-2 (q8) and 7.40e-2 (kvarn) against a 5e-2 ceiling, while `qwen3_5` passed.
The issue suspected the indexed-MoE fixture rewrite in PR #370.

## What it actually was

Two separate things, neither of them the fixture rewrite.

### 1. A real defect, now fixed

A prefill batch with exactly ONE trailing row computed that row's attention
catastrophically wrong — 4.2e-1 on dense `qwen3_5`, 8.7e-1 on
`qwen3_5_moe_indexed`. Fixed in
`2026-09-02-single-row-trailing-prefill-batch.md`. It was invisible to this gate
because the gate ran only at `--n 300` (a 44-row tail), and it was NOT what #377
reported — that symptom is present at every `n`.

### 2. The reported symptom: a metric artifact

The ceiling was applied to the MAX relative error over ~300 rows. Sweeping KVarN
width on the reported fixture:

| bits | p99 | max | rows>1e-2 | worst row |
|---|---|---|---|---|
| 2 | 1.38e-1 | 2.20e-1 | 38 | 207 |
| 4 | 3.68e-2 | 7.40e-2 | 36 | 160 |
| 8 | 8.90e-3 | 6.80e-2 | 2 | 154 |

The distribution behaves exactly as quantisation error should: rows over 1e-2
fall 18x from 2-bit to 8-bit, and p99 improves 15x. **The max does not** —
2.20e-1 → 7.40e-2 → 6.80e-2, essentially flat past 4-bit — and the identity of
the worst row changes at every width.

That is the signature of a heavy tail, not a fixed defect. A max over 300 rows is
whatever the single most extreme token happens to do, so it stays around 7e-2 no
matter how good the cache is. **The 5e-2 max-based ceiling was unreachable for
this fixture by construction**, and no amount of code fixing would have cleared
it.

## Fix

The gate asserts on **p99** instead, with the max still printed (a large gap
between the two is itself informative).

    tiny-prefill-gate: ran=4 fail=0 skip=2 not-measured=7

      qwen3_5              q8 p99 5.75e-3   kvarn p99 2.05e-2
      qwen3_5_moe_indexed  q8 p99 1.13e-2   kvarn p99 3.68e-2

**The discrimination is intact** — verified, not assumed. Re-running the whole
gate with `HIPFIRE_KVARN_BITS=2`, which is genuinely lossy:

    FAIL hidden-state divergence kvarn = 1.38e-1 exceeds ceiling 5e-2
    FAIL one-row trailing batch (n=257) kvarn = 1.28e-1 exceeds 5e-2
    tiny-prefill-gate: ran=4 fail=2 skip=2 not-measured=7

So the gate still fails bad KV and now passes good KV, which the max-based
version could not do.

## Why this took a while to see

The max is the natural first choice for "did anything diverge", and it is the
right statistic for an invariant that must hold EXACTLY — which is why the fp32
row keeps it. It is the wrong statistic for a tolerance on lossy storage, where
the question is whether the bulk is sound. Both live in this gate and they need
different treatment.

The precision sweep is what separated them, and it is the same test that
disproved an earlier hypothesis in this investigation: if a quantity does not
respond to precision, it is not quantisation error, whatever it looks like.
