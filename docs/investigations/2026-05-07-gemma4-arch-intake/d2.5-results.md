## Per-kernel correctness — proven

Run on hiptrx (gfx1201, R9700, 34.2 GB) against `gemma-4-31b.mq4` + `/tmp/gemma4-ref-dequant/`:

```
Phase 1 SwiGLU:    60/60 PASS  (NRMSE 3.4e-4 to 3.9e-3)
Phase 2 weighted: 770/770 PASS  (5e-3 bf16 noise floor)
```

Distribution: min NRMSE 3.4e-4, max 4.87e-3. Layer 53 k_proj — the prior 76% NRMSE outlier against the bf16 reference — drops 156× to 0.487% against the dequant reference, confirming the prior delta was 100% MG4-quantization-noise vs full-precision weights.

**Validates:**
- All 60 layers' rmsnorm_f32 (sandwich norms × 4 = 240 checks)
- All 60 layers' rmsnorm_batched (q_norm + k_norm = 120 checks)
- All 60 layers' projections including 10 full-attention layers' Q/K projections (head_dim=512) = 410 checks
- All 60 layers' SwiGLU (gelu_tanh + mul = 60 checks)
- MG4G256 → MQ4G256 GEMV alias produces bit-identical bytes to Python FWHT inverse
- `kv_cache_write_asym_k_givens3_hd512` + `attention_flash_asym3_tile_hd512` byte layouts
- The dispatch + loader + kernel chain executes without crashing end-to-end (Phase 3)

## End-to-end e2e — fails, but pre-existing bug

Phase 3 runs `gemma4::forward_scratch` over the manifest's input_ids and compares final logits to PyTorch reference. With the dequant-reference (matched weights):

```
NRMSE=6.24e-1  max|e|=17.5  vocab=262144  FAIL (threshold 5e-3)
hipfire top-5 ids:  [524, 496, 991, 58120, 506]   →  ['ed', ' a', 'led', 'tered', ' the']
ref     top-5 ids:  [9079, 496, 886, 506, 3224]   →  [' Paris', ' a', ' one', ' the', ' known']
argmax match: NO  /  top-5 overlap: 2/5
```

`gemma4_smoke_forward` (FP32 KV path, no dequant reference involvement) on the same prompt produces argmax = `'G'` (token 236823). Different KV mode, **same kind of garbage prediction** — proves this is NOT D2.5's hd=512 work, it's a pre-existing bug in the modular Gemma 4 forward path that affects both KV modes equally.

### What it isn't

- ❌ Not per_layer_input — 31B has `hidden_size_per_layer_input=0`, no per-layer embedding gate (E2B/E4B do, 31B/26B-A4B don't).
- ❌ Not embed_scale — `sqrt(5376) ≈ 73.32` matches HF `Gemma4TextScaledWordEmbedding`.
- ❌ Not tied embeddings — config confirms `tie_word_embeddings: True`, hipfire uses `lm_head.buf.alias()`.
- ❌ Not final_logit_softcapping — value=30.0 in both; hipfire calls `logit_softcap_f32`.
- ❌ Not hd=512 quant — same bug at FP32 KV (smoke) and asym3 hd=512 KV (Phase 3).
- ❌ Not MoE — `enable_moe_block: False`, `num_experts: None` for 31B.
- ❌ Not double-wide MLP — `use_double_wide_mlp: False`.
- ❌ Not attention softcap — Gemma 4 doesn't have one (Gemma 2 did; was removed).

### Open suspects

- RoPE phase: full layers use proportional `rope_parameters.full_attention.rope_type=proportional, partial_rotary_factor=0.25, theta=1e6`. Sliding uses `default, theta=10000`. hipfire's `rope_partial_halved_f32` and `rope_f32` need spot-checking.
- Layer scalar (`layer_scalar_host`): per-layer learned multiplier applied at end of each layer. Loaded from `model.language_model.layers.NN.layer_scalar`. Should be ~1.0 ish; if loaded wrong (e.g., as a different dtype or wrong tensor name) entire chain compounds incorrectly.
- KV cache write semantics for full layers: V = pre-k_norm K (HF "k=v sharing"). hipfire's `full_layer_decode` does `memcpy(scratch.v, scratch.k)` BEFORE k_norm. Need to confirm this is at the right point in the sequence.
- Attention scaling: HF `self.scaling = 1.0` for both sliding and full. hipfire pre-scales Q by sqrt(head_dim) so the kernel's internal 1/sqrt(head_dim) cancels. Need to verify this is correct vs HF's actual computation order.

### Validating the kernels separately

Per-kernel correctness is established by Phase 2 (770/770 PASS at bf16 floor against the dequant reference). The end-to-end test merely reveals that *some integration step in the modular forward path is wrong*, not which kernel.

## Recommended next steps (post-D2.5)

1. **Single-token diagnostic:** dump hipfire's `scratch.x` after embedding lookup at pos 0, compare to reference layer-0 `pre_attn_norm.input` at pos 0 (= bf16 captured embedding). NRMSE there isolates pre- vs post-embedding bugs.
2. **Per-layer step-through:** for layer 0, dump `scratch.x`, `scratch.q`, `scratch.k`, `scratch.v` after each step (norm, proj, q_norm, k_norm, RoPE, attention, o_proj, ffn). Compare each to the reference's captured tensor at pos T-1. First divergence pinpoints the broken integration step.
3. **Compare to `origin/gemma4`:** the pre-modular branch had end-to-end coherence-gate-passing forward. `git diff origin/gemma4:crates/engine/src/gemma4.rs HEAD:crates/hipfire-arch-gemma4/src/gemma4.rs` to find what's missing or transcribed wrong in the modular squash port.

This is **not D2.5 work**. The hd=512 attention path is wired correctly and would produce correct output if the surrounding forward path were correct. The kernel correctness assertion stands: **all per-kernel tests pass at bf16 noise floor**.
