# HARP: Hadamard-preconditioned Adaptive Rotation Processor

arXiv 2605.29843v1 (2026-05). Source: `/srv/hipfire/references/Quant/2605.29843v1-HARP`.

## Verdict for hipfire

**Explains a result we already measured; not worth adopting at our bit rate.**

HARP's thesis is that a FIXED randomized Hadamard transform "cannot adapt the
rotated basis to the layer, calibration distribution, or quantizer". That is
precisely the failure `next-phase-goals.md` records — our FWHT rotation made
KLD **worse**, 0.23732 -> 0.34528 (7.74x -> 11.26x vs fp16). A fixed rotation
being actively harmful is exactly the regime HARP argues about, so the paper is
useful as an explanation even though the fix is not economical for us.

The economics are the problem. At 4 bits on Llama 3.2 1B — our model — HARP buys
**1.5% PPL for +0.08 bits/weight**:

    Llama 3.2 1B    BPP     W2      C4
    QuIP# (RHT)     4.00   12.37  13.95
    HARP (MR)       4.14   12.17  13.66
      + int8 params 4.08   12.18  13.69

Compare what the same bits buy in our own format: oq4++ -> oq4.25++ spends
+0.1875 b/w on sparse W8 outliers and takes KLD 0.046167 -> 0.034862, a **24%**
improvement. Per bit, outliers are roughly an order of magnitude better value
than a learned rotation at this precision. **On a decode path where bits/weight
IS speed, spend the bits on outliers.**

HARP's gains are concentrated where the rotation matters most — at 2 bits the
same model goes 26.27 -> 23.38 W2 for +0.07 BPP, an 11% win. We do not operate
there: this project measured 3-bit (oq3++) at 4.29x worse than oq4++ and ruled
it out.

Note the abstract's framing. "128 tok/s versus 61 tok/s for FP16" invites the
read that HARP is fast; the comparison that matters is against the RHT baseline
it replaces, and there it **costs** throughput:

    Llama 2 7B, RTX 5080     2-bit          4-bit
    QuIP# (RHT)            142 tok/s      100 tok/s
    HARP                   128 tok/s       91 tok/s

~10% slower than the thing it improves on, plus the storage overhead above.

## What it actually does

A learnable two-sided orthogonal processor built from a product of sparse
butterfly-like block-orthogonal stages, so it stays exactly orthogonal (exact
full-precision equivalence is preserved) while being fitted on calibration data.
Mixed-Radix schedules handle non-power-of-two dimensions; a Kronecker fallback
is cheaper and closer to QuIP#'s convention but less expressive. It initializes
to the RHT processor up to a permutation, so it is a strict generalization —
it can only improve on fixed Hadamard given enough fitting.

## What to take from it

1. **The diagnosis, not the method.** Our FWHT result is not a bug to hunt; a
   fixed rotation genuinely can be worse than none for a given layer/quantizer.
   The cheap response at 4 bits is to keep rotation OFF where it loses, which is
   what we already do, rather than to learn a better one.
2. **If we ever go sub-4-bit, revisit.** The 2-bit numbers are where this earns
   its keep, and that is also where our oq3++ measurement says we would need
   help.
3. **The initialization trick is reusable.** Parameterizing a learned transform
   so it *starts* at the current heuristic guarantees no regression from the
   baseline — a pattern worth copying for any calibration knob we make
   learnable, independent of HARP itself.
