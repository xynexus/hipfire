# M1 scope — correctness prerequisites, re-verified 2026-08-25

Scoping pass for §M1 of `2026-08-09-v2-daemon-module-major-multistream.md`.
Every claim below was checked against the tree on 2026-08-25 (master
`aed057006`), not carried from the plan's prose.

**Why this doc exists.** §M1a's own history is the warning: its first sizing
called the fix "a signature change across every `upload_raw` call site", which
would have been 693 sites and a large risky change. Measuring showed the
asymmetry only bites on *churning* callers, of which there were three, and the
real fix was ~3 call sites. **Scope M1 by measurement or repeat that mistake.**

## M1b — the global was removed; the sharing was relocated

This is the finding that changes the scope, and it is not what the plan's
"LANDED"-adjacent prose implies.

**What landed.** `static SAMPLER_STATE: AtomicU32` is gone (`sampler.rs:684`
records it in past tense). `SamplerRng` exists and `StreamTable::admit` takes
one per stream (`daemon/stream.rs:186`).

**What did not.** Three things, each verifiable in one grep:

1. **Nothing samples through it.** `daemon/stream.rs:181` says so outright:
   *"The rng is a slot: the daemon's decode path does not sample through
   `SamplerRng` yet, and greedy decode never consults it."*
2. **No request seed reaches it.** Admission passes `SamplerRng::from_entropy()`.
   `SamplerRng::from_seed` has **zero production call sites** — only
   `hipfire-runtime/examples/*`. So per-request seeds are not honoured, and
   §M1b's exit criterion (two seeds, `temperature=0.8`, batched, byte-identical
   to solo) cannot be met today.
3. **The RNG state is still shared per model, not per stream.** The GPU sampler
   round-trips its state through `Qwen35Scratch::sample_buf`, a single `[2]`
   tensor (`qwen35/mod.rs:502`, "token_id + rng"). That scratch is
   `LoadedModel::q35_scratch` — **one per loaded model**, `take()`n and returned
   around each generate (`generate.rs:189/203`). Every session on a model shares
   it.

Point 3 means §M1b's stated failure mode — *"stream i's token depends on how
many others sampled before it"* — is **still live**, having moved from a
`static` into shared GPU scratch. Removing the global did not remove the
sharing. Today the `take()` serializes generate per model so it does not
misbehave; under module-major interleaving it will, which is exactly M1's
premise that these are latent bugs a churning executor makes certain.

`take()` is itself worth noting for M3: two concurrent generates on one model
cannot both hold the scratch.

**Remaining M1b work, in dependency order:**

1. Make the per-stream `SamplerRng` the actual source of the sampler's state,
   and seed it from the request seed instead of `from_entropy()`. Requires
   either a per-stream `sample_buf` or passing seed/state through the existing
   round-trip; the per-model scratch is the obstacle either way.
2. Batched multi-row sampling. Sampling is *already* on-device, but per call,
   single row, with an 8-byte D2H each (`generate.rs:2029`). N interleaved
   streams therefore cost N launches and N round trips — the "N D2H round trips"
   §M1b warned about. This is the `row_seed` + `sample_rows` kernel; grep
   confirms **neither exists** (the only `sample_rows` hits are unrelated
   calibration code).

**Hazard, restated from the plan and still correct:** step 1 changes sampled
output for every `temperature>0` request, deliberately. **Greedy baselines must
not move.** If a greedy tiny-quant or tiny-state hash shifts, the change is
wrong. That is a cheap, sharp check — run it.

## M1d — two globals left, both small

| global | site | size |
|---|---|---|

| `load_progress::SINK` | `load_progress.rs:34` | 280-line file, 14 `report` call sites. A `THREAD_SINK` thread-local already exists and is consulted first (`:37`, `:52`), so the per-thread escape is half-built |

### `hipfire_steer` — re-scoped 2026-08-25, and the plan's framing is stale

The plan names `hipfire_steer::{SESSION, ACTIVE, EPOCH}`. **`SESSION` singular no
longer exists**: it is `SESSIONS: HashMap<SteerKey, Session>`, already per-key,
reached through a `CURRENT_KEY` thread-local plus a `SteerKeyGuard` scope guard —
the same shape `load_progress` uses.

The two surviving globals are deliberate, with soundness arguments in place:
`ACTIVE` is a fast-path gate meaning "any session is active" (it *cannot* be
per-key, because the hot path checks the gate before it knows the key), and
`EPOCH` is one counter across keys, sound only because `ApplyCache` also compares
its key — a comment records that an earlier justification for the shared counter
was wrong and how the key comparison closes it.

**So the remaining work here is not removing globals. It is that nothing keys
into the per-key machinery.** `SteerKeyGuard` has ZERO installers outside the
steer crate — the only external mention is a comment in
`hipfire-arch-gemma3/src/forward.rs:784`. Every hot-path call
(`maybe_steer_block`, `maybe_steer_block_batched` in qwen35's decode, lowered and
prefill paths) resolves `with_current_key` against a `CURRENT_KEY` that is never
set, i.e. `SteerKey::default()`. All streams therefore share one session.

`daemon/handlers/steer.rs`'s own module doc agrees, and states the constraint
plainly: *"the session is process-global and outlives the model it was captured
against, which is why load and unload clear it defensively — and why two steer
ops must never interleave."* Under module-major interleaving that last clause
stops being a rule callers can honour.

This is the same shape as M1b: the capability landed, the use did not. Sizing it
means answering how a stream's `SteerKey` is assigned by the steer handlers
(capture/apply are registered process-globally today), which is a design question
about the steer API, not a mechanical wiring job — and is why it is **deferred**
rather than estimated here.

Neither is large. The plan's ordering note is the real argument for doing them:
they become *wrong*, not merely ugly, the moment two streams interleave — a
steer session or a load-progress sink belonging to stream A is observed by
stream B.

`load_progress` is the cheaper of the two and its `THREAD_SINK` suggests the
intended shape already. `hipfire_steer` is the one with real API surface.

## Suggested order

1. **`load_progress::SINK`** — smallest, and the thread-local half exists.
2. **`hipfire_steer` globals** — contained in one crate, ~8 entry points.
3. **M1b step 1** (per-stream RNG actually wired + request seeds). Gated on
   deciding the `sample_buf` / per-model-scratch question, which is the real
   work; the RNG plumbing is already there.
4. **M1b step 2** (`sample_rows` batched kernel). Only pays off once the
   executor actually interleaves N streams — sequence it with M3, not before.

M1a needs nothing further unless the residual API trap is closed, which §1.6's
slabs do as part of M5.

## What this doc did NOT verify

- Whether `Qwen35Scratch` has other per-model state that becomes cross-stream
  under interleaving. `sample_buf` was found by following the sampler; the rest
  of the struct was not audited, and it is ~120 fields.
- Whether non-qwen35 arches share the same scratch shape.
- M1c's reaper under real panic conditions — only its four unit tests were
  confirmed present, not re-run.
